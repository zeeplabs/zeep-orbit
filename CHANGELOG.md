## [1.5.0] — 2026-08-17

### Added

- **Dual-license model for the repository, with a full enterprise license text.** The root `LICENSE` now documents that `internal/enterprise/` (and its future frontend mirror `internal/dashboard/ui/src/enterprise/`) is licensed separately from the rest of the MIT-licensed repository. `internal/enterprise/LICENSE` (English, controlling) and `internal/enterprise/LICENSE.pt-BR.md` (Portuguese translation) hold the Enterprise Source License text; `COMMERCIAL_TERMS.md`/`COMMERCIAL_TERMS.pt-BR.md` hold the subscription terms. Legal counsel sign-off obtained; the draft/pending-review notices have been removed from all four documents. No enterprise licensing logic (verification, gating, etc.) exists yet — this change only establishes the folder/license boundary and the legal text. See `LICENSING.md`, `docs/docs/enterprise-licensing.md`, and `.specs/features/enterprise-licensing/`.
- **10 new read-only MCP tools** let an AI agent inspect an app's own configuration and operational surface without asking a human to check the Dashboard UI: `orbit_get_app`, `orbit_list_table_policies`, `orbit_list_app_members`, `orbit_list_app_tokens`, `orbit_list_app_auth_providers`, `orbit_list_my_pats`, `orbit_list_webhooks`, `orbit_get_webhook`, `orbit_list_webhook_deliveries`, `orbit_get_logs_metrics`. Every tool authorizes through the exact same `GetApp`/role-check path (or ownership scoping) its REST equivalent already uses — no new permission model — and never returns a secret/credential value its REST equivalent doesn't already redact.
- **4 new safe mutation MCP tools** let an AI agent evolve an existing table's schema and manage webhooks without the risk of the full-replace `PUT .../tables/{tableId}` endpoint: `orbit_add_table_column` and `orbit_add_table_index` add exactly one new column/index, merged server-side against the table's current stored definition — the request can never omit or corrupt an existing column/index, unlike a naive full-replace resend. `orbit_create_webhook` and `orbit_save_webhook_event_mapping` wrap the existing, already-additive webhook endpoints. Table-schema tools require `role.CanWrite()`; webhook tools require the stricter `role.CanManage()`, matching each operation's existing REST authorization tier exactly.

### Fixed

- **`GET /docs/{app}/openapi.json` could serve a stale spec missing recently added tables.** The response carried no `Cache-Control` header, so a browser or intermediate proxy could cache the spec from before a table was added and keep serving it after — the endpoint's data was always correct on an uncached request. Responses are now marked `Cache-Control: no-store`.

### Security

- **The dashboard API and the MCP tool `orbit_list_apps` no longer return an app's real credentials in plaintext.** `GET /dashboard/api/apps`, `GET /dashboard/api/apps/{id}`, and `orbit_list_apps` were all serializing the app's storage config (AWS `access_key_id`/`secret_access_key`) and every configured auth provider's OAuth `client_secret` — plus, on `GET .../apps/{id}` before an existing partial fix, the app's own `jwt_secret` — to any caller who could see the app at all (any app member, not just an admin). Confirmed as a live incident on a production app before this fix. Responses now carry only what a dashboard UI legitimately needs to display (bucket/region/client_id/etc.) plus a `client_secret_set` boolean; `orbit_get_app_schema` was never affected (its response shape never carried these fields). **If you have apps with a configured storage bucket or OAuth login provider, treat those credentials as exposed and rotate them** — this fix stops further disclosure, it doesn't invalidate what may already have been read.
- **Saving an app's Login settings without retyping its Google OAuth `client_secret` no longer silently deletes that secret and breaks the app's Google login.** `PUT /dashboard/api/apps/{id}` did a raw overwrite of the stored `auth_providers` config; the dashboard's Login tab never re-populates the `client_secret` field from a GET (it can't — see above), so every save that didn't involve retyping the secret sent an empty value, wiping it. Auth provider updates now merge onto the existing stored config field-by-field, matching the merge-on-absent-key convention already used for the separate system-wide auth providers config: an absent, `null`, or empty-string field in the request keeps whatever's already stored; a non-empty value still overwrites (secret rotation keeps working).
- **Turning an app's Google login toggle off in the dashboard now actually disables it.** The Login tab only sent `auth_providers` in its save request when the toggle was on, so switching it off changed nothing server-side — the toggle looked saved but the provider stayed enabled in the database. The toggle's state is now always sent explicitly.
- Credential redaction (both the per-app and the system-wide auth provider config) now projects onto an allow-list of known-safe display fields instead of deleting the one known secret field name — a credential stored under an unexpected or nested key can no longer slip through a redaction path unmasked. The system-wide config's write-response endpoint (`PUT /dashboard/api/config/auth/providers/{provider}`) also stopped echoing the caller's raw request body, which could otherwise hand back a real `client_secret` the caller never actually sent (the same merge-pulls-in-the-stored-secret pattern as the app-level bug above). A malformed (non-object) provider config payload no longer risks a nil-map panic on either merge path.

## [1.4.0] — 2026-08-16

### Added

- **MCP server** — Zeep Orbit now exposes a Model Context Protocol endpoint (`/dashboard/mcp`) so an AI coding agent (Claude Code, Claude Desktop, Cursor, Codex, OpenCode) can create and manage apps, tables, RLS modes, and row policies through the same operations the dashboard's REST API already performs — one tool per existing endpoint, not a parallel code path. Two auth methods: **Personal Access Tokens** (bearer, created/listed/revoked from the dashboard) for CLI-style clients, and **OAuth 2.1 with PKCE + dynamic client registration** (RFC 7591) for clients like Claude Desktop that have no way to paste a static token. The OAuth flow restricts registered `redirect_uris` to `https://` (or `http://` on loopback, for native/CLI clients per RFC 8252), single-uses and PKCE-binds authorization codes, rotates refresh tokens with reuse detection (a replayed token revokes its whole token family), and verifies `client_id` at every token exchange (authorization_code and refresh_token grants alike).
- **A dedicated "MCP" page in the dashboard** (Deployment section of the sidebar) explains how to connect an AI coding agent to this Orbit instance's MCP server: the live endpoint URL with a copy action, a plain-language explanation of the two auth methods, and copy-pasteable, syntax-highlighted config snippets for each of the four PAT-based clients. Personal access token management (create, list, revoke) moved here from its previous home behind an unlabeled key icon in the sidebar footer.
- **A superadmin-only "Registered OAuth clients" section on the MCP page** lists every client that has dynamically self-registered against this instance's OAuth endpoint (registration is unauthenticated by RFC 7591 design, so this would otherwise be invisible) and lets a superadmin delete one — which cascades to revoke every authorization code and access/refresh token pair that client was ever issued.
- **`ORBIT_PUBLIC_URL`** (optional env var) pins the base URL the OAuth 2.1 metadata document (`/.well-known/oauth-authorization-server`) advertises its endpoints under. Without it, the URL is derived from the request's `Host`/`X-Forwarded-Proto` headers — set this if Orbit runs without a reverse proxy that validates those headers, so an MCP client can't be pointed at a spoofed token endpoint via a forged `Host` header.
- **The OAuth consent flow resumes correctly after a login (including via Google SSO) instead of dropping an admin back on the dashboard home.** An unauthenticated admin hitting the consent screen is bounced to login with the original request preserved in `return_to`; after login (password or Google, including a first-time Google setup step), the admin lands back where they started rather than at `/apps`.

## [1.3.0] — 2026-08-13

### Added

- **`rls: "policy"` — a third Row-Level Security mode that removes the automatic `owner_id = $sub` filter entirely.** Until now, `rls: "enabled"` behaved exactly like `rls: "owner"`: every list/get/update/delete got an automatic `owner_id = $sub` filter applied on top of any table policy, so a policy could only narrow what a user saw within their own rows — never widen it to another user's (e.g. "an admin role sees every post", "an RH role sees every employee"). A table with `rls: "policy"` gets `ENABLE ROW LEVEL SECURITY` at creation, before any policy exists (native Postgres fail-closed: zero policies denies all reads/writes for the end-user role, with no app-layer check backing it up), and from then on visibility and write permission are 100% delegated to the table's own policies — `owner_id` still gets populated automatically on every `INSERT` made by an authenticated end-user, and is now referenceable inside a policy clause (`owner_id = claim.sub`), but it is never injected as an automatic filter. Unlike `"owner"`/`"enabled"`, the column is nullable for `"policy"` — a write with no end-user identity behind it (e.g. an inbound webhook delivery, below) leaves it `NULL` rather than failing. Existing `rls: ""`/`"owner"`/`"enabled"` tables are unaffected. The Dashboard lets an existing table switch between `"enabled"` and `"policy"` without recreating it or losing data, with an explicit warning that the switch changes who sees which rows.
- **Inbound webhooks** — an app owner can now create a webhook that receives events pushed by an external provider (e.g. Google Workspace) and writes them into an app table, no code required. Each webhook gets a unique URL with a per-webhook token (`/hooks/{webhookId}/{token}`); a new webhook starts in capture mode, recording the first real payload it receives without writing to any table. From the captured sample, the owner picks a target table and click-links fields to columns per event-type value (insert/update/delete, with a match-key column for update/delete), then activates the webhook so subsequent real calls apply the mapping. Every call — success, unmapped event, invalid token, duplicate, write failure — is recorded in a delivery log visible from the app's new "Webhooks" tab, retained for 30 days. Writes run under a dedicated RLS role (`webhook`, via `table_policies`), so an app owner must grant it a policy on the target table. Outbound webhooks (Orbit firing events on row changes) remain a separate, not-yet-built feature.
- **Inbound webhooks: provider verification handshake support** — a call carrying a top-level `challenge` string (the convention Slack's Events API and similar providers use to verify a new webhook URL) is now echoed back verbatim as `{"challenge": "..."}` with a `200`, bypassing capture/mapping entirely and logged as `verification_challenge` in the delivery log — instead of failing the provider's "challenge_failed" check.
- **Inbound webhooks: a webhook's name, HTTP method, and event-shape paths can now be edited** after creation, via a new "Edit" button on the Webhooks tab (`PATCH /dashboard/api/apps/{id}/webhooks/{webhookId}`). Token, status, and captured sample are untouched — this was a known gap flagged during the pre-release review (no way to fix a typo or a wrong path without deleting and recreating the webhook, which would also mean generating a new token and losing the delivery history's continuity).
- **Table policies: a Policy Templates screen is now the default way to create a row policy**, replacing the technical Column/Operator/Claim/Logic form as the first thing an app owner sees. Six named templates ("Only the owner sees/edits", "All signed-in users with the selected role can view", "Nobody edits, read-only", "Visible when a value matches", "Open read, write restricted to the owner", plus the non-actionable "Blocked by default" explainer) cover the common cases without exposing RLS internals; the composite template ("Open read, write restricted to the owner") applies 3 policies in sequence and, on partial failure, keeps whatever was already created and lets a retry skip what's done. The old technical form is still there behind a new "Advanced mode" toggle — unchanged, no capability removed — alongside a new "Help" drawer with worked examples for anything the templates don't cover.

### Changed

- **Table editor: the "relationships" and "indexes" tutorials moved from a centered modal into a side drawer** (same `FormDrawer` pattern used by the Policy Templates help drawer), and their explanations were rewritten in plain language with a bookkeeping/spreadsheet analogy for non-technical readers, replacing the more technical original copy. The content is now authored in Markdown (rendered via a new shared `MarkdownContent` component, backed by `react-markdown`) instead of `react-i18next`'s `<Trans>` tag-mapping, so future edits don't require juggling numbered placeholder tags across two locale files.
- **Inbound webhooks: the full callback URL is now always visible**, not just once at creation/rotation. The token is stored AES-256-GCM encrypted (same pattern as the GitHub App/S3 config credentials) instead of a one-way SHA-256 hash, so it can be decrypted for display on every load of the Webhooks tab — a real product need, since re-pasting a webhook URL into a provider's admin panel weeks after creating it was previously impossible without rotating first. A webhook created before this change has a token that can no longer be decrypted; rotating it once produces a working link. The token is encrypted under its own dedicated key (new optional `WEBHOOK_TOKEN_ENCRYPTION_KEY`, falling back to `DASHBOARD_BOOTSTRAP_SECRET`) instead of reusing `GOOGLE_OAUTH_ENCRYPTION_KEY`, so rotating either secret doesn't also invalidate the other's ciphertexts.
- **Inbound webhooks: the mapping editor now warns when the target table's row policies don't yet permit the `webhook` role for every command the delivery path actually issues** — `select` for both the update/delete match-key lookup and Postgres's own evaluation of SELECT policies against `INSERT ... RETURNING *` (so an insert mapping needs `insert` **and** `select`, not just `insert`), plus `update`/`delete` for the write itself (an update/delete mapping needs `update` when the app has soft delete enabled, `delete` otherwise — matching `query.BuildDelete`'s actual behavior, not just the mapping's own action label). The check no longer skips at zero currently-saved policies: deleting a table's last policy never disables RLS (default-deny must stay explicit), so a zero-policy table can still be fully locked down, not necessarily open. The mapping form now shows a live inline warning — updating as the target table/action change, not just at save — naming the table and the specific missing command(s) and pointing at the Policies tab; the check itself is best-effort (it may warn even when the table was never RLS-protected at all) rather than a guarantee, and surfaces its own failure distinctly if the policy lookup itself can't load.
- **Inbound webhooks: the dashboard now polls while a webhook is waiting for its first sample**, instead of requiring a manual page reload to see it once the external provider's call arrives — the capture happens outside any mutation this tab knows about, so nothing else was invalidating that query.

### Fixed

- **The app-details tab strip no longer forces the whole page to scroll horizontally on narrower screens.** Adding the Webhooks tab pushed the strip past the sidebar's available width; the strip itself now scrolls independently (`overflow-x-auto`, non-shrinking triggers), and `<main>` got the `min-w-0` its CSS grid track needed to actually bound that scroll area instead of growing to fit its content.
- **Destructive confirmations across tables, policies, and webhooks now use the same in-app `ConfirmDialog` instead of the browser's native `confirm()`** (switching a table's RLS mode, deleting a table, deleting a policy, rotating a webhook token, deleting a webhook) — consistent styling/copy with every other confirmation in the dashboard, translated in both locales, instead of an untranslatable native browser prompt.
- **Creating a table with RLS "Public" (or leaving RLS at its default when "require RLS by default" is off) no longer fails.** The Dashboard sent `rls: "disabled"` for this case, but the backend has only ever accepted `""`, `"owner"`, `"enabled"`, or `"policy"` — `"disabled"` was rejected outright by `validateTableInput`, breaking the default "Add table" flow whenever an app didn't require RLS by default, and breaking explicit selection of "Public" on any table. Pre-existing bug, unrelated to any specific feature; the frontend now sends `""` for this case, matching what the backend has always expected.
- **Inbound webhooks: webhook token no longer appears in application logs.** The `/hooks/{webhookId}/{token}` path was logged verbatim (zap + the dashboard's Logs ring buffer), so a global `auditor` role — which has no direct access to the Webhooks tab — could read a live write token straight out of `/dashboard/api/logs`. The path is now redacted before it reaches either log sink, and the request/response body for this route is no longer captured at all (it's a third-party provider's payload, not diagnostic data). **Found again, more broadly, by an independent Verifier pass**: the dashboard's own `GET`/`POST`/`PATCH` webhook subscription endpoints (list/get/create/update/rotate-token) always echo the plaintext token in their JSON response (by design — see "the full callback URL is now always visible" below), and those response bodies were still being captured into the same log ring buffer, reopening the same leak through a different path. Response/request body capture is now skipped for these endpoints too.
- **Inbound webhooks: the public delivery route is now rate limited (120 req/min per IP) and caps the request body at 1 MiB.** Previously it ran unauthenticated and unbounded — same tier as `/health` — so anyone who knew a webhook's id (visible in its dashboard URL) could flood `webhook_deliveries` with `invalid_token` rows or send an oversized body straight into `captured_sample`.
- **Inbound webhooks: a failed delivery (`write_error`, `row_not_found`) no longer permanently blocks its `event_id` from ever being retried.** The dedup check counted any delivery with a matching `event_id` as "already processed," including ones that failed to write — so a transient failure (e.g. an RLS policy not yet granted to the `webhook` role) followed by the provider's expected retry was silently swallowed as `duplicate_skipped` instead of applying the write, losing the event for good.
- **Inbound webhooks: an update/delete mapping whose match-key column isn't actually unique no longer silently writes to an arbitrary row.** The lookup had no `LIMIT`/uniqueness check, so a match key resolving to more than one row (e.g. a non-unique `email` column) picked whichever row Postgres happened to return first and applied the write to it without any indication in the delivery log or the app owner's data. It's now detected and rejected as a new `ambiguous_match` outcome (`409`), with no write applied.
- **Inbound webhooks: saving a mapping with a blank `event_type_value` or an empty `field_mappings` is now rejected server-side (`400`)**, not just by the frontend form. A blank event-type value would have silently matched every payload missing that field; an empty field-mappings list would have 500'd at delivery time instead of failing at save time.
- **Inbound webhooks: delivery outcome and mapping action labels are now translated** (`webhooks.outcome.*`/`webhookMapping.action.*`, both locales) instead of rendering the raw internal value (e.g. `duplicate_skipped`) directly in the UI.
- **Inbound webhooks: a verification-challenge delivery no longer persists the full inbound payload** — only the challenge value is stored, so a legacy verification `token` some providers (e.g. Slack's older Events API shape) send alongside `challenge` doesn't sit in the 30-day delivery log.
- **Inbound webhooks: the mapping editor's sample-fields/table-columns panel is no longer a fixed 2-column grid on narrow screens** — single column below the `sm` breakpoint.
- **Row policies: creating an `insert`-action policy on any table no longer fails.** `BuildPolicySQL` always generated a `USING (...)` clause regardless of action, but Postgres rejects a `USING` clause on an `INSERT` policy outright ("only WITH CHECK expression allowed for INSERT") — so a table's first insert policy (for any role, on any app, not just webhooks) would 500 with a raw Postgres error instead of creating. Found while fixing the webhook mapping editor's RLS warning, whose own remediation path (add an insert policy for the `webhook` role) was blocked by this. `USING` is now emitted only for select/update/delete; `WITH CHECK` only for insert/update.
- **Inbound webhooks: an insert delivery into a table with RLS `"policy"` no longer fails outright.** `owner_id` was `NOT NULL` on every RLS-enabled table regardless of mode, but a webhook delivery has no end-user identity to put there — every insert violated the constraint and the provider saw an infinite retry loop. The column is now nullable for `"policy"` mode specifically (see the `rls: "policy"` entry above); `"owner"`/`"enabled"` are unaffected, and an existing table switching into `"policy"` has the constraint relaxed at that point too.
- **Inbound webhooks: request/response bodies over 2 KiB are no longer truncated before the handler ever sees them.** The request logger's body-capture buffer was reused as the actual request body forwarded downstream, so any delivery payload over 2 KiB (the norm for most providers) arrived truncated and failed JSON parsing — the mapping editor's advertised 1 MiB body cap never had a chance to apply. Logging now captures a bounded prefix without consuming the rest of the stream.
- **Inbound webhooks: deleting an event mapping is now scoped to its own webhook.** `DELETE .../webhooks/{webhookId}/mappings/{mappingId}` deleted by mapping id alone, so any app with dashboard access could delete another app's mapping by guessing/reusing its UUID — no ownership check.
- **Inbound webhooks: two deliveries with the same `event_id` arriving at once (a provider retrying a slow request, the normal at-least-once case) could both write, instead of the second being skipped as a duplicate.** The dedup check-then-write wasn't atomic and the underlying index isn't unique by design (a failed delivery must be allowed to retry under the same `event_id`); concurrent requests are now serialized per `(webhook_id, event_id)` with a Postgres advisory lock. The lock's held connection now comes from a small pool dedicated to it, not the main pool — the first version borrowed straight from the main pool (`MaxConns=10`) for the lock's entire duration, so ≥10 concurrent deliveries with *distinct* event ids (no actual dedup contention between them) could exhaust every connection and deadlock the whole process, dashboard included; caught in a second review pass before release, not shipped.
- **Inbound webhooks: an update/delete mapping's match-key lookup no longer counts a soft-deleted row.** On an app with soft delete on, a live row sharing its match-key value with a soft-deleted one was always flagged `ambiguous_match`, and an update targeting only a soft-deleted row would resurrect its content instead of correctly reporting `row_not_found`. The lookup now excludes `deleted_at IS NOT NULL` rows, matching `query.BuildDelete`/`BuildUpdate`'s own filter.
- **The public webhook delivery route's rate limit is no longer shared across every tenant on the same replica.** It was keyed by source IP, which behind this service's non-sticky load balancer is the balancer's own address — one noisy provider could 429 every other app's webhooks hitting the same replica. Now keyed by `webhookId`, scoping the budget to one webhook subscription.
- **Six 500 responses in the row CRUD/table-drop endpoints leaked the raw Postgres error message to the client** (`internal/dashboard/handler.go` — drop table, insert/update row and their RETURNING re-read, delete row), instead of the fixed generic message `writeError` is meant to enforce. The real error was already logged server-side in every case; only the public-facing message is changed.
- **A handful of backend validation errors were in Portuguese** (`internal/query/builder.go`, one message in `internal/dashboard/handler.go`) despite the API contract requiring English error strings, with localization left to the frontend. Translated; no error code or shape changed.
- **Inbound webhooks: the mapping editor's RLS-policy warning couldn't have flagged the exact bug above** — an insert mapping only checked for an `insert` policy, but Postgres also evaluates `SELECT` policies against `INSERT ... RETURNING *` (which every insert delivery issues), so it now also requires a `select` policy for the `webhook` role. The warning no longer skips its check when the table currently has zero saved policies, either — deleting a table's last policy never disables RLS (default-deny must stay explicit), so a zero-policy table isn't necessarily unrestricted. If the policy check itself fails to load, the form now says so explicitly instead of silently showing no warning.

## [1.1.0] — 2026-08-10

### Added

- **App user email/phone editing** — the "Usuários do App" edit drawer (previously role-only) now also lets admins correct an end-user's `email` and `phone`. New `PUT /dashboard/api/apps/{id}/users/{userId}` (replaces `PUT .../role`) accepts `{email, phone, role}` together; changing the email resets `email_confirmed_at` and clears the user's active sessions (forces re-authentication), and a duplicate email now returns a clear `409` instead of a raw constraint error. Status (active/inactive) is unchanged — still a separate table-row toggle.
- **Users tab on the app detail screen** — app-user management (list, edit, activate/deactivate) is now a tab on `/apps/:id` right after "Login providers", instead of a standalone page only reachable from the apps list card. The old `/apps/:id/users` route now redirects to `/apps/:id?tab=users`; the app card's "Users" action opens the app and jumps straight to the tab.
- **Country-aware phone mask for app user editing** — the app-user edit drawer's phone field is no longer free text: a new `PhoneInput` component (`@zeeptech/toolkit`) pairs a country select (235 countries, flag + dial code, Brazil first) with a live-masked input, so the entered number always matches the selected country's format. Phone is stored as `+{dialCode}{digits}` for round-trip editing; `PUT /dashboard/api/apps/{id}/users/{userId}` now rejects a non-empty `phone` that isn't a loose E.164 shape (`+` + 8–15 digits) with a `400`.
- **Configurable end-user business roles per app** — apps used to be stuck with the hardcoded `member` default for the `role` column on `_auth_users`. A new "End-user roles" section on the app's settings lets admins define their own role list (chips instead of a raw CSV input), backed by `PUT /dashboard/api/apps/{id}/roles` (full-list replace, not a merge). Removing a role still assigned to at least one end user or referenced by at least one row policy is blocked with a `409` (`{role, endUserCount, policyCount}`) instead of silently orphaning data. The app-user edit drawer and the row-policies role-chip picker both read from this list, and flag any role a user/policy already has that has since been removed from it rather than dropping it silently.
- **End-user row policies (native Postgres RLS)** — app admins can now define row-level access rules per table/action (`select`/`insert`/`update`/`delete`) combining an end-user's business `role` (new claim on the login JWT, backed by a new `role` column on `_auth_users`, default `member`) with a condition on the row's own data (e.g. `requester_id != claim:sub`), enforced natively by Postgres (`CREATE POLICY`/`ROW LEVEL SECURITY`), not by a Go-layer filter — so the rule holds even against a direct Postgres connection, not just the Orbit REST API. End-user requests now run under a dedicated `zeep_app_enduser` Postgres role (`SET LOCAL ROLE`, no ownership/`BYPASSRLS`) instead of the schema-owning role; the Dashboard, purge job and provisioner are unaffected since they keep running as the owner role, which Postgres already exempts from RLS by default. Clauses support `=`/`!=`/`IN`/`NOT IN`/`>`/`<`/`>=`/`<=`/`IS NULL`/`IS NOT NULL` and compose with `AND`/`OR` (left-to-right fold, fully parenthesized). Tables with no policy keep today's exact behavior — nothing changes for existing apps. Configured from a new "Policies" tab on the table detail view (builder form — no free-SQL editor exposed), with a `POST/GET/DELETE /dashboard/api/apps/{id}/tables/{table}/policies` API underneath. App admins can now also set an end user's business `role` directly from the "Usuários do App" edit drawer (part of the combined `PUT /dashboard/api/apps/{id}/users/{userId}` from the email/phone editing change above) — previously the column existed but had no admin-facing way to change it away from the `member` default. The schema builder's foreign-key dropdown (`TableCard`) now also offers `_auth_users` as a reference target for `uuid` columns when the app has email auth enabled — the backend already accepted this FK shape (`internal/config/validate.go`'s `_auth_users`-specific branch), but there was no UI path to create it short of the raw API; only `id` is offered as the target column, matching the backend's restriction.

### Fixed

- **End-user row policies: existing apps no longer lose end-user data access on upgrade.** Every end-user request now runs as the dedicated `zeep_app_enduser` Postgres role, but the `GRANT`/`ALTER DEFAULT PRIVILEGES` that let that role see an app's tables previously only ran when an app's schema was touched through the Dashboard (create/edit). An app untouched since upgrading would 500 on every end-user request. `zeep serve` now backfills the grant for every app already in the registry once at boot (`Provisioner.BackfillEnduserGrants`); a single app with a stale schema logs a warning instead of blocking every other app (or the whole server) from starting. **Upgrade note:** the boot process creates the `zeep_app_enduser` role if it doesn't exist yet, which requires the configured Postgres user to have `CREATEROLE` (or be a superuser) — a restricted managed-Postgres role without it will fail to boot with a clear Postgres permission error.
- **`GET/PUT /dashboard/api/config/system` no longer risks silently wiping global config on a transient DB read failure.** `GetSystemConfig` used to swallow every read error and return a zero-value config; `UpdateSystemConfig`'s merge-then-write would then persist that zero value over the real one (losing global S3 storage credentials, resetting retention/statement-timeout settings) instead of failing the request with a `500`.
- **Login/token-refresh rate limiting was a no-op.** The auth rate limiter keyed on `RemoteAddr`, which includes the ephemeral source port — every new TCP connection got its own bucket, so a brute-force loop was never actually throttled. Now keys on host only. Both the auth and per-app rate limiters also stopped accumulating one map entry per distinct client IP forever; stale entries are swept once per window.
- **`PhoneInput` no longer resets to Brazil when picking a country before typing a number.** Country selection is now tracked independently of the current (possibly empty) phone value, so choosing a country on an empty field — the common case when editing a user who has no phone yet — sticks instead of silently reverting on the next render.
- CI now runs the Go test suite against a real Postgres service instead of skipping every integration test (including the ones that exercise RLS enforcement) for lack of `TEST_DATABASE_URL`. Runs with `-p 1` since several packages share that one database and race on the `zeep_system` schema when run in parallel.

### Fixed

- **`ResolveAppRole` resolved the axes in the wrong order** — a platform-wide `admin`/`auditor` who also had an explicit per-app membership (e.g. `editor` on a specific app) was resolved as `viewer` on that app instead of their actual membership role, because the platform-wide fallback was checked before the `app_members` lookup. Explicit per-app membership now wins over the platform-wide fallback, as the spec always intended.
- **`GET /dashboard/api/apps/{id}` leaked the app's `jwt_secret`** to any role with read access to the app (including `viewer`/`auditor`, via the bug above) — the sibling `Create`/`Update` handlers already redacted it before responding, but `GetApp` didn't. Anyone with the secret can forge a valid end-user token for that app. Now redacted like the other two handlers.
- **Several per-app mutation endpoints had no role gate at all** — `DeactivateAppUser`/`ActivateAppUser`/`ResetAppUserSessions`, `CreateAppToken`/`RevokeAppToken`/`RegenerateAppSecret`, and `UpdateAppTable`/`DeleteAppTable` looked up the app but discarded the caller's resolved role, relying only on "some effective access" instead of `CanWrite()`/`CanManage()` like their sibling endpoints already did. A `viewer` or `editor` (per-app) could deactivate end users, reset their sessions, rotate the app's `jwt_secret`, or drop tables. Now gated at the same level as their sibling endpoints.
- **Data Browser create/update/delete accepted writes from read-only roles** — the three handlers checked only whether the caller had *any* access to the app (`ListOwnedAppNames`, which for `superadmin`/`admin`/`auditor` returns "no filter" and for per-app members doesn't distinguish role), never `CanWrite()`. A per-app `viewer` or a platform-wide `auditor` could insert/update/delete rows in any app's data. Now resolved via `ResolveAppRoleByName` + `CanWrite()`, matching the spec's original intent ("writes are still blocked at the handler via `CanWrite()`").
- **The "≥1 admin per app" invariant never actually ran** — the last-admin guard in `UpdateAppMemberRole`/`RemoveAppMember` used `SELECT COUNT(*) ... FOR UPDATE`, which Postgres rejects outright ("FOR UPDATE is not allowed with aggregate functions"). Every PATCH/DELETE targeting a member who *is* an admin therefore failed with 500 — both the cases that should have been rejected with 400 ("app must have at least one admin") and the legitimate ones, so an app admin could not be demoted or removed at all. The count now runs as an aggregate over a locked subquery, keeping the row locks that protect against two concurrent demotions.
- **`DELETE /dashboard/api/apps/{id}` answered 500 instead of 403** for a caller without `CanManage` — the handler had no role gate of its own and mapped only `ErrNotFound` from the store, so the store's `ErrForbidden` fell through to the generic 500 branch. Now gated like `UpdateApp`, with `ErrForbidden` mapped explicitly as a second line of defense.

## [0.1.11] — 2026-07-02

### Fixed

- **Google OAuth "session expired" on callback** — OAuth `state` was stored in an in-memory map per pod. With multiple replicas and no sticky session, `/login` and `/callback` could land on different pods, so the state was never found and login always failed with "Login expired, please try again". State is now a stateless, HMAC-signed token (embeds `redirect` + expiry, signed with the app's JWT secret) — any replica can validate it without shared storage.
- **API docs branding** — Generated OpenAPI spec title and docs index page now show "API Documentation" instead of the hardcoded "zeep-orbit" name.

### Changed

- **Dashboard copy** — Login page and app subtitle updated to "Database-first backend platform" / "Create backends from your database", with new supporting subtitle text.
