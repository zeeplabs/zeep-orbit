## [Unreleased]

### Added

- **Table relationships (foreign keys) and indexes** in the schema builder — table config now accepts `references` (table/column/`on_delete`) and `indexes`. Adds schema validation (unknown table/column, invalid `on_delete`, index name collisions, circular FK dependencies), topological table ordering so referenced tables are created/altered before their dependents, idempotent index provisioning (no implicit drop), and `DropTable` now refuses to drop a table still referenced by another table's FK with a clear error instead of leaking a raw Postgres error. Data Browser's `TableCard` surfaces FKs and indexes read-only in the UI.
- **`GET /api/deploy-provider/recent-deploys`** (`integrations-handoff-parity` spec, superadmin-only). Aggregates the most recent Render deploys across up to 15 frontend apps with a deploy service already created (`render.Client.ListDeploys`, a new `GET /services/{id}/deploys` call), merges and sorts by creation time, returns the 10 most recent as `{appName, status: "Live"|"Failed", time: "Xh ago"}`. No new table, no background job — fetched live on every call under a 5s total timeout; a Render failure for one app is logged and skipped, never fails the whole request. Now surfaced in the UI too — Deploy providers tab shows a real "Recent Deploys" list (was missing entirely) with an empty state when there's nothing to show yet. New i18n keys `integrations.recentDeploys{Title,Empty,Error}` (en + pt-BR).
- **Role-based access (4 platform roles)** — dashboard `admin`/`auditor`/`member` users now have permissions gated by a single matrix (`HasPlatformPermission`, mirrored in `permissions.ts` for the UI). New `useHasPlatformPermission` hook lets components omit — not just disable — items the current role can't access. Sidebar (desktop) and MobileNav (mobile bottom-sheet) now resolve visibility through this matrix; `RequireRole` guards stay in place for direct URL navigation. `superadmin` is unaffected. Part of the `dashboard-global-roles` spec (T-02 + T-07/T-08 of 9).
- **Per-app roles (admin / editor / viewer)** — every app (backend or frontend) now has a per-user membership row with one of three roles. The `ResolveAppRole` function is the single source of truth for "what role does this user have on this app?" and is called by every handler that needs to gate a per-app action. The two axes cross cleanly: a `superadmin` global is admin on every app without explicit membership; `admin`/`auditor` global get read-only access to any app via the cross-spec `CanReadAnyApp` extension (the `dashboard-global-roles` T-06 cross-spec link, now satisfied). Backend enforcement is wired into the existing handlers (list/read/update/delete + table CRUD + sync credentials + reveal key + archive); frontend apps have the same treatment. New "Members" tab in the app details page lets admins add, change role, and remove members. The "≥1 admin" invariant is enforced inside the store via transaction + a row lock on the admin rows (see Fixed below for a bug in the original query), so two concurrent admins cannot both see "there's still another admin" and both proceed to demote themselves. Every mutation is audit-logged (`app_member.added` / `role_changed` / `removed`). Part of the `rbac-per-app` spec (T-01..T-09 of 12; T-07 reserved, T-10..T-12 follow-up).
- **Require RLS by default** (Settings → Database): when enabled, a new app table created without an explicit access level defaults to Restricted (owner-scoped RLS) instead of Public. Off by default; only applies when the app has email auth enabled (Restricted requires it), and never overrides an access level the client sends explicitly.
- Dashboard create-table form now defaults new tables to Restricted (owner-scoped) when "Require RLS by default" is enabled and the app has email auth — previously the setting only affected API/omitted-`rls` creates.

- **`GET /dashboard/api/data-browser/apps` now returns a `count` (row count) per table** — used to redesign the Data Browser tree to match the redesign handoff (always-expanded app groups with folder icons, row-count badge per table). Reuses the existing `query.BuildList` count-query path (no filters, same soft-delete-aware `CountSQL`), so it costs one extra `COUNT(*)` per table on every tree load. Toolbar (icon-only Filters/Export CSV/Refresh), column headers (plain lowercase, no type badge) and pagination footer (unboxed "Showing X–Y of Z", icon-only prev/next) were restyled to match as well.

- **SDK code snippets now have real syntax highlighting** (`prismjs`, new dependency) instead of plain monospace text — matches the redesign handoff's coloring (keywords/imports in `--primary`, string literals in `--accent`, numbers in `--warning`). Custom token-to-token-mapping stylesheet (`src/styles/prism.css`) instead of a stock Prism theme, so it follows the app's existing color tokens (and dark/light mode) rather than hardcoded hex values. Covers all 6 languages already on the page (TypeScript, Go, Python, Rust, Java, PHP); install-command lines are left unhighlighted (plain text), matching the handoff.

- **`GET /dashboard/api/audit-log` gains `category` and `user_email` filters** — `category` (`create`/`modify`/`delete`/`auth`) maps to a fixed, explicit list of action strings per bucket (`auditCategories` in `audit_store.go`, not a fuzzy pattern match); `user_email` does a `ILIKE '%...%'` substring match, replacing the old exact-match `user` (user ID) param since the Audit log page's user filter changed from a superadmin dropdown to a free-text email search (matches the redesign handoff). The `action` exact-match filter is untouched. Audit log page also gets the handoff's segmented All/Create/Modify/Delete/Auth pill filter (was a dropdown), raw monospace `action` strings as colored chips (was a translated label), and a single-line "ResourceType: name" resource column (was two stacked lines) — new i18n keys `audit.category{All,Create,Modify,Delete,Auth}` / `audit.filterUserPlaceholder` (en + pt-BR); orphaned `audit.filterAction`/`audit.filterUser` and the now-unused `auditActionLabel`/`ACTION_LABELS` (frontend) removed.

- **Dashboard Users page matches the redesign handoff.** New info banner explaining the dashboard-level role vs. per-app roles; role badge now covers all 4 platform roles (Superadmin/Admin/Auditor/Member — was Superadmin/Admin only, even though the backend already supported 4); Create-user drawer reordered (Name → Email → Temporary password → Role) with the role picker redone as selectable cards (icon + description per role, matching `handoff/`'s `createUserRoleOptions`) instead of a plain dropdown — the "Superadmin" option is hidden from the picker unless the actor is already a superadmin, mirroring the backend's `CanCreateUserWithRole` restriction. Sign-in column now shows the real multi-color Google "G" mark instead of a generic account icon. New i18n keys `users.role{Superadmin,Admin,Auditor,Member}Desc`, `users.roleFootnote`, `users.dashboardRoleInfo`, `users.emailPlaceholder`, `users.reset2faSoon` (en + pt-BR). A disabled "Reset 2FA" (`phonelink_lock`) action was added per the handoff's row actions, but left inert — 2FA is a net-new feature (`handoff/README.md`'s feature list) with no backend today; wiring it up is separate follow-up work, not part of this visual-parity change.

- **Retention period + soft-delete purge** (Settings → Database, `dashboard-settings-consolidation` spec, slice S2.1): a new global `retention_days` setting (default 0 = off) drives a background job that hard-deletes soft-deleted rows older than the configured window, across every app table, on a 6h cadence. Off by default and gated on soft-delete being enabled; each run — including zero-row runs — writes an `audit_log` entry (`system.purge.run`) so the job's activity is auditable. Enabling purge (raising the value above 0) prompts a confirm dialog in the UI, since the action is irreversible. New i18n keys `settings.retentionDays` / `settings.retentionDaysHint` / `settings.retentionDaysConfirm` (en + pt-BR).

- **End-user row policies (native Postgres RLS)** — app admins can now define row-level access rules per table/action (`select`/`insert`/`update`/`delete`) combining an end-user's business `role` (new claim on the login JWT, backed by a new `role` column on `_auth_users`, default `member`) with a condition on the row's own data (e.g. `requester_id != claim:sub`), enforced natively by Postgres (`CREATE POLICY`/`ROW LEVEL SECURITY`), not by a Go-layer filter — so the rule holds even against a direct Postgres connection, not just the Orbit REST API. End-user requests now run under a dedicated `zeep_app_enduser` Postgres role (`SET LOCAL ROLE`, no ownership/`BYPASSRLS`) instead of the schema-owning role; the Dashboard, purge job and provisioner are unaffected since they keep running as the owner role, which Postgres already exempts from RLS by default. Clauses support `=`/`!=`/`IN`/`NOT IN`/`>`/`<`/`>=`/`<=`/`IS NULL`/`IS NOT NULL` and compose with `AND`/`OR` (left-to-right fold, fully parenthesized). Tables with no policy keep today's exact behavior — nothing changes for existing apps. Configured from a new "Policies" tab on the table detail view (builder form — no free-SQL editor exposed), with a `POST/GET/DELETE /dashboard/api/apps/{id}/tables/{table}/policies` API underneath.

### Fixed

- **`ResolveAppRole` resolved the axes in the wrong order** — a platform-wide `admin`/`auditor` who also had an explicit per-app membership (e.g. `editor` on a specific app) was resolved as `viewer` on that app instead of their actual membership role, because the platform-wide fallback was checked before the `app_members` lookup. Explicit per-app membership now wins over the platform-wide fallback, as the spec always intended.
- **`GET /dashboard/api/apps/{id}` leaked the app's `jwt_secret`** to any role with read access to the app (including `viewer`/`auditor`, via the bug above) — the sibling `Create`/`Update` handlers already redacted it before responding, but `GetApp` didn't. Anyone with the secret can forge a valid end-user token for that app. Now redacted like the other two handlers.
- **Several per-app mutation endpoints had no role gate at all** — `DeactivateAppUser`/`ActivateAppUser`/`ResetAppUserSessions`, `CreateAppToken`/`RevokeAppToken`/`RegenerateAppSecret`, and `UpdateAppTable`/`DeleteAppTable` looked up the app but discarded the caller's resolved role, relying only on "some effective access" instead of `CanWrite()`/`CanManage()` like their sibling endpoints already did. A `viewer` or `editor` (per-app) could deactivate end users, reset their sessions, rotate the app's `jwt_secret`, or drop tables. Now gated at the same level as their sibling endpoints.
- **Data Browser create/update/delete accepted writes from read-only roles** — the three handlers checked only whether the caller had *any* access to the app (`ListOwnedAppNames`, which for `superadmin`/`admin`/`auditor` returns "no filter" and for per-app members doesn't distinguish role), never `CanWrite()`. A per-app `viewer` or a platform-wide `auditor` could insert/update/delete rows in any app's data. Now resolved via `ResolveAppRoleByName` + `CanWrite()`, matching the spec's original intent ("writes are still blocked at the handler via `CanWrite()`").
- **The "≥1 admin per app" invariant never actually ran** — the last-admin guard in `UpdateAppMemberRole`/`RemoveAppMember` used `SELECT COUNT(*) ... FOR UPDATE`, which Postgres rejects outright ("FOR UPDATE is not allowed with aggregate functions"). Every PATCH/DELETE targeting a member who *is* an admin therefore failed with 500 — both the cases that should have been rejected with 400 ("app must have at least one admin") and the legitimate ones, so an app admin could not be demoted or removed at all. The count now runs as an aggregate over a locked subquery, keeping the row locks that protect against two concurrent demotions.
- **`DELETE /dashboard/api/apps/{id}` answered 500 instead of 403** for a caller without `CanManage` — the handler had no role gate of its own and mapped only `ErrNotFound` from the store, so the store's `ErrForbidden` fell through to the generic 500 branch. Now gated like `UpdateApp`, with `ErrForbidden` mapped explicitly as a second line of defense.
